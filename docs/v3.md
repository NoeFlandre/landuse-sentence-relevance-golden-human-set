# V3 workflow (candidate pool shipped, annotation seed shipped; resumable annotation UI; publication paused)

V3 extends the human set from the 154 adjudicated V2 rows to a state of 300 rows across three sources. The project implemented these items: the streaming adapters, the oversized candidate pool and geographic preflight (issue #6), and the deterministic annotation seed (issue #7). The resumable annotation UI is available when you select it explicitly. The default command still runs the V2 pipeline. The V3 seed has frozen V2 rows and unlabeled fresh slots. Its benchmark is still `data/benchmark/v2-adjudicated.csv`.

This page records the contracts of the implemented adapter, candidate pool, annotation seed, and resumable UI. Issue [#10](https://github.com/NoeFlandre/landuse-sentence-relevance-golden-human-set/issues/10) tracks the V3 publication. The project implemented the candidate pool and the geographic preflight together with the resumable UI. For the V2 workflow, refer to [Data sources and models](data-sources.md) and [Annotation](annotation.md).

## Planned upstream datasets

The V3 adapters stream three public Hugging Face datasets. As in V2, the commit SHA pins each revision. The adapters never materialize a dataset locally. `V3Settings` holds the pins. The environment cannot override them on purpose.

| Source | Dataset | Pinned revision | Configuration and split that the settings name |
| --- | --- | --- | --- |
| Description tag | [OSM polygon description tag](https://huggingface.co/datasets/NoeFlandre/osm-polygon-description-tag) | `fec858b679f5ee7e87f0ecfaaa6b7223b2a7f5e2` | `language-v1`/`train` sentence records with `language_code` and `sentences`. The adapter joins them to `default`/`train` for the geometry. |
| Wikipedia | [OSM polygon Wikidata and Wikipedia](https://huggingface.co/datasets/NoeFlandre/osm-polygon-wikidata-and-wikipedia) | `f48c5aaaec6aecd63ecf5c195565cc2787597f1e` | `wikipedia_sentences`/`wikipedia_sentences` records with `language`, `project`, and `section_index` |
| Website tag | [OSM polygon website tag](https://huggingface.co/datasets/NoeFlandre/osm-polygon-website-tag) | `5c8e56a50b5679118a28aef057af002209f80a5e` | `default`/`polygons`. Its rows already have the pre-split sentence columns and their `*_language` fields. |

The website dataset does not publish a separate sentence configuration. Its pre-split sentences are columns in `default`/`polygons`. The settings therefore read that split. They do not read a sentence-level split. The `language-v1` records of the description dataset have no coordinates. The join below resolves the geometry.

### Planned sentence and language contract

All three upstream datasets already publish sentence-level records and language metadata. The V3 adapters use them as they are:

- The sentences come from the upstream sentence fields. **No local splitter runs.** V2 uses SaT-12L-sm today. The V3 adapters do not use it.
- The English filter uses only the upstream language metadata. **No local language model runs.** V2 uses CommonLingua today. The V3 adapters do not use it.
- The adapters restrict the Wikipedia rows to `project=wikipedia` and English articles. **They exclude Wikivoyage.** They never read the `wikivoyage_sentences` and `wikivoyage_sections` configurations. This is the same rule that V2 uses to exclude Wikivoyage.
- The Wikipedia selection stays contextual. As in V2, the adapters reject title-only sentences and lead-only sentences. The pinned revision does not publish an `is_lead` column or an `is_title` column. The rule therefore uses the columns that the revision publishes and what they hold in the recorded schema fixture:
    - The **lead** is `section_index` 0. In the recorded shard, every lead row also has an empty `heading` at `level` 0 with an empty `section_path`. No body row has an empty heading. The adapter therefore also reads an empty heading as the lead.
    - A **section title** reaches the sentence table as the first sentence of a body section. The table renders it with the MediaWiki edit marker (`[ edit ]` or `[ edit | edit source ]`). In the recorded shard, all 592 first sentences of body sections start with that marker. The marker appears nowhere else. When the adapter rejects those rows, it drops only heading lines.
    - `sentence_index` alone never decides this. The adapter keeps a body sentence that is not a heading line, whatever its index.
- Some sentence records have no coordinates. For these records, bounded streaming joins back to the polygon records resolve the geolocation. This keeps the provenance deterministic. The join reads the polygon or geometry side one time across all of its shards. It keeps only a small projection of each row: identity, coordinates, place name, region, and source URL. A sentence therefore finds its polygon when the two rows are in shards with different numbers. Two limits bound the join: `max_rows_per_shard` rows for each shard, and at most `max_join_entries` keys at the same time.
- The provenance goes with every candidate. It comes from the columns that each pinned revision publishes:
    - `region` comes from the `region` column of the Wikipedia polygons and the website polygons. The description dataset does not publish `region`. The adapter derives it from `source_pbf`. It removes the extract suffixes (`afghanistan-latest.osm.pbf` becomes `afghanistan`). The sibling datasets of the same extract publish exactly that label. The fallback therefore reproduces the published value. It does not invent a value.
    - `source_url` is the `osm_url` of a description geometry. For a website row, it is the `website` or the `contact_website`. For Wikipedia, it is a URL that the adapter derives from `page_id` (`https://en.wikipedia.org/?curid=…`), because the sentence table does not publish a URL column.

### The recorded upstream schemas validate the projections

`tests/fixtures/v3_upstream_schema.json` records the Parquet schema of all five pinned streams. It also records the sampled facts that the Wikipedia rules and the region rules use. The unit tests assert every projected column against that file. A projection can therefore never name a column that a pinned revision does not publish. When a pin changes, record the file again with `uv run python scripts/record_v3_schema.py`.

`scripts/streaming_smoke.py` is the network gate. It opens all five V3 streams with the exact production projections at the pinned revisions. It reports each projected column that the stream does not return. Then it builds a few real candidates for each source from one pinned shard each.

## Candidate pool and geographic preflight

Run the builder from the project checkout:

```bash
./scripts/uv-seagate run python scripts/build_v3_candidate_pool.py
```

The builder streams the five pinned upstream inputs through the V3 adapters. It reserves every H3 cell in `data/benchmark/v2-adjudicated.csv`. For each globally unique H3 resolution-3 cell, it keeps one candidate that it selects deterministically. By default, it finalizes at least 400 cells for each source. If the source reservoirs or the shortfalls of the V2-seeded quotas are not sufficient, it fails before an annotation workflow can start. Its stdout is a compact JSON preflight summary. It never prints candidate sentences or raw upstream rows.

The builder writes the V3 working artifacts only under the `V3Settings` data root on the Seagate project drive:

- `results/candidates/v3/progress.json` is an atomic, resumable checkpoint of compact candidate metadata. The builder writes it during the collection and after an interrupted stream.
- `results/candidates/v3/pool.json` is the finalized compact reservoir and its metadata. The builder writes it only after the geographic preflight and the quota preflight succeed.

The builder streams the upstream rows and discards them. The V2 benchmark stays committed and immutable. The builder uses its rows only to derive the seed plan and the set of reserved cells.

## V2 reuse and quota arithmetic

`data/benchmark/v2-adjudicated.csv` is immutable. Nobody edits it. V3 seeds its state from that file. It shows only the remaining rows for future human annotation.

| Source | Seeded from V2 | Fresh unlabeled slots | V3 target total (yes / no) |
| --- | --- | --- | --- |
| Wikipedia | 99 | 1 | 100 (50 / 50) |
| Website | 54 | 46 | 100 (50 / 50) |
| Description | 0 | 100 | 100 (50 / 50) |
| **Total** | **153** | **147** | **300** |

V2 has 100 Wikipedia rows (49 yes, 51 no) and 54 website rows (31 yes, 23 no). V3 reuses 99 Wikipedia rows. It leaves out one surplus `no` row from the V3 quota. It adds one Wikipedia `yes` row to reach 50 / 50. V3 reuses all 54 website rows. 46 fresh website rows close the gap for each label. The description source gives 100 completely new rows. The seeded V2 rows count toward the progress metrics. The UI never shows them for reannotation. The pending rows have no human label.

## Annotation seed and resume behavior

First build the reservoir of issue #6. Then run the seed builder from the project checkout:

```bash
./scripts/uv-seagate run python scripts/build_v3_annotation_seed.py
```

The builder loads the frozen V2 benchmark as read-only. It validates the existing candidate-pool preflight. It writes `results/annotations/seeds/v3.json`. Its metadata records the benchmark SHA-256, the candidate-pool digest, the quota matrix, and the selection policy. The output is a compact JSON summary. It has the counts and the deterministic reason for the excluded V2 row. It never prints candidate sentences. It never invents labels.

If the process stops before the atomic write, run it again. It selects the same source-by-label slots. If the seed exists and its metadata matches, the builder reuses it. It does not open the upstream streams again. It does not select new rows. The builder rejects a changed benchmark, candidate pool, seed, or quota matrix. It does not mix the states silently.

## Resumable annotation UI

Run the V3 UI explicitly from the project checkout:

```bash
ANNOTATION_VERSION=v3 ./scripts/uv-seagate run landuse-annotate
```

The entrypoint first builds the V3 candidate pool and the seed. It starts only after the candidate preflight succeeds. If the preflight fails, the entrypoint raises the error before it creates a web server or a V3 session. The default command without `ANNOTATION_VERSION=v3` still runs V2.

The page shows these items:

- the total progress for all 300 initial rows;
- the progress for each source: Wikipedia, website, and description;
- the Yes and No counts against their targets; and
- each remaining source-by-label quota.

The metrics count the seeded V2 rows. The UI never shows the seeded V2 rows for reannotation. The 147 initial fresh V3 rows appear first. The UI offers reserve candidates only for a source where the observed labels still leave a quota short. The UI stops at once when every source-by-label quota is complete.

Every label, relabel, and removal replaces the V3 JSONL session through atomic persistence. When the process reloads, it validates the saved candidate content against the immutable V3 seed. It resumes at the next unlabeled fresh row. The V3 workflow has no publisher. When the local session is complete, the workflow never uploads or publishes V3 data.

## Storage paths

V3 keeps its own files next to the V2 files on the Seagate project drive. It mirrors the V2 layout under a `v3` prefix. It does not reuse a V2 path. `V3Settings` defines the V3 paths below. Issue #6 writes the candidate pool and the progress checkpoint. Issue #7 writes the annotation seed. Issue #8 writes the V3 session through the UI during the human annotation.

| Artifact | `Settings` (V2) path | `V3Settings` path |
| --- | --- | --- |
| Candidate pool | `results/candidates/v2/pool.json` | `results/candidates/v3/pool.json` |
| Candidate progress checkpoint | `results/candidates/v2/progress.json` | `results/candidates/v3/progress.json` |
| Annotation seed | - | `results/annotations/seeds/v3.json` |
| Annotation session | `results/annotations/sessions/v2-wikipedia.jsonl` | `results/annotations/sessions/v3.jsonl` |
| Runtime and auth state | `state/runtime-cache`, `state/huggingface-auth` | unchanged |

No V3 path overwrites the V2 state. The candidate build saves compact metadata checkpoints atomically. It can resume from an interrupted source stream. The project writes the seed atomically. The seed can resume from a matching state. It does not contain human labels for fresh rows. The UI session is a separate atomic V3 JSONL file. It does not change `data/benchmark/v2-adjudicated.csv`.

## Limitations

- The V3 UI is local only. There is no published V3 split. There is no `v3` benchmark file in `data/benchmark/`. A separate issue tracks the publication.
- The publication behavior in issue #10 is design intent. It can change before the release.
- V3 changes nothing in V2. The released `v2` artifacts, splits, and tags are frozen. The [versioning policy](versioning.md) still applies.
- The design takes the upstream sentence segmentation and language labels. The project does not correct upstream segmentation errors or language errors locally.
- The coverage is one sentence for each H3 resolution-3 cell. This limits the geographic density. It does not guarantee a balanced regional representation.
- The description source is new in V3. It has no V2 rows to reuse. It depends completely on fresh annotation.
