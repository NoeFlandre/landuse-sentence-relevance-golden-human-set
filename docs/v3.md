# V3 workflow (planned, paused)

V3 would extend the human set from the 154 adjudicated V2 rows to 300 rows
across three sources. The work is **paused and not implemented**: the repository
currently ships only the V2 pipeline, its settings, and its paths. No V3 code,
V3 settings, or V3 benchmark exists, and the benchmark to use remains
`data/benchmark/v2-adjudicated.csv`.

This page records the agreed V3 design so the public documentation matches the
paused state. Everything below is planned behavior tracked in issues
[#4](https://github.com/NoeFlandre/landuse-sentence-relevance-golden-human-set/issues/4)
to
[#8](https://github.com/NoeFlandre/landuse-sentence-relevance-golden-human-set/issues/8),
not behavior that exists today. For what the code does now, see
[Data sources and models](data-sources.md) and [Annotation](annotation.md).

## What exists today

| Aspect | Implemented V2 behavior | Planned V3 design |
| --- | --- | --- |
| Sources | Two: Wikipedia sections and website-tag text | Three: description tag, Wikipedia sentences, website-tag sentences |
| Sentence splitting | SaT-12L-sm runs locally | No local splitter; upstream sentence records only |
| Language filtering | CommonLingua runs locally on website text | No local language model; upstream language metadata only |
| Settings | `src/landuse_sentence_relevance/config.py` pins the two V2 dataset revisions and the V2 model revisions | V3 dataset revisions and settings are not in `config.py`; adding them is issue #4 |
| Paths | `results/candidates/v2/…`, `results/annotations/sessions/v2-wikipedia.jsonl` | Separate V3 paths, not yet defined in the repository |
| Rows | 154 adjudicated rows, two sources | 300 rows, 100 per source |

## Planned upstream datasets

V3 would stream three public Hugging Face datasets and, as in V2, would pin each
revision by commit SHA and never materialize a dataset locally. The pinned V3
revisions do not exist in `config.py` yet; only the V2 Wikipedia and website
revisions are pinned there today.

| Source | Dataset | Records the design would use |
| --- | --- | --- |
| Description tag | [OSM polygon description tag](https://huggingface.co/datasets/NoeFlandre/osm-polygon-description-tag) | `language-v1` sentence records with `language_code` and `sentences` |
| Wikipedia | [OSM polygon Wikidata and Wikipedia](https://huggingface.co/datasets/NoeFlandre/osm-polygon-wikidata-and-wikipedia) | `wikipedia_sentences` records with `language`, `project`, and `section_index` |
| Website tag | [OSM polygon website tag](https://huggingface.co/datasets/NoeFlandre/osm-polygon-website-tag) | `website_sentences` and `contact_website_sentences` with their `*_language` fields |

### Planned sentence and language contract

All three upstream datasets already publish sentence-level records and language
metadata, so the V3 design consumes them as they are:

- Sentences would come from the upstream sentence fields. **No local splitter
  would run**: SaT-12L-sm is used by V2 today and would not be used for V3.
- English filtering would use upstream language metadata only. **No local
  language model would run**: CommonLingua is used by V2 today and would not be
  used for V3.
- Wikipedia rows would be restricted to `project=wikipedia` and English
  articles. **Wikivoyage is excluded**: the `wikivoyage_sentences` and
  `wikivoyage_sections` configurations would never be read, matching the V2
  rule that already excludes Wikivoyage.
- Wikipedia selection would stay contextual: title-only and lead-only sentences
  rejected, as in V2.
- Where sentence records carry no coordinates, geolocation would be resolved
  with bounded streaming joins back to the polygon records, keeping provenance
  deterministic.

## Planned candidate pool and geographic preflight

- At least 400 fresh candidates per source by default, one candidate per
  globally unique H3 resolution-3 cell.
- Every H3 cell already occupied by a V2 row reserved, so V3 additions never
  collide with the frozen benchmark.
- Deterministic selection spread across the world.
- A preflight check verifying that enough candidates and distinct cells exist
  for the V3 quotas before the annotation UI starts.
- Only compact candidate metadata and checkpoints written to the Seagate project
  drive; upstream rows streamed and discarded.

## Planned V2 reuse and quota arithmetic

`data/benchmark/v2-adjudicated.csv` is immutable and would never be edited. V3
would seed its state from that file and annotate only the remaining rows.

| Source | Seeded from V2 | New annotations | V3 total (yes / no) |
| --- | --- | --- | --- |
| Wikipedia | 99 | 1 | 100 (50 / 50) |
| Website | 54 | 46 | 100 (50 / 50) |
| Description | 0 | 100 | 100 (50 / 50) |
| **Total** | **153** | **147** | **300** |

V2 holds 100 Wikipedia rows (49 yes, 51 no) and 54 website rows (31 yes, 23 no).
V3 would reuse 99 Wikipedia rows — one surplus `no` row left out of the V3 quota
— and add a single Wikipedia `yes` row to reach 50 / 50. All 54 website rows
would be reused, so 46 new website rows close the per-label gap, and the
description source would contribute 100 entirely new rows. Seeded V2 rows would
count toward the progress metrics but would never be presented for
reannotation.

## Planned storage and resume behavior

V3 would keep its own files beside the V2 ones on the Seagate project drive,
mirroring the V2 layout under a `v3` prefix rather than reusing any V2 path. The
V2 paths below are the ones the code uses today; the V3 column is design intent
and is not defined in `config.py`.

| Artifact | Implemented V2 path | Planned V3 equivalent |
| --- | --- | --- |
| Candidate pool | `results/candidates/v2/pool.json` | a separate pool file under `results/candidates/v3/` |
| Candidate progress checkpoint | `results/candidates/v2/progress.json` | a separate checkpoint under `results/candidates/v3/` |
| Annotation session | `results/annotations/sessions/v2-wikipedia.jsonl` | a separate V3 session file under `results/annotations/sessions/` |
| Runtime and auth state | `state/runtime-cache`, `state/huggingface-auth` | unchanged |

No V3 path would overwrite V2 state. Candidate building would checkpoint after
each pass and resume with only the remaining cell quota, so an interrupted run
does not repeat completed source work. The annotation session would be appended
atomically, so labeling, relabeling, removing a row, quitting, and resuming
behave exactly as they do in V2 today. The UI would show total and per-source
progress, yes/no counts, and the remaining quotas, and would start only after
the candidate preflight succeeds.

## Limitations

- V3 is paused and unimplemented. There is no V3 code path, no V3 setting in
  `config.py`, no published V3 split, and no `v3` benchmark file under
  `data/benchmark/`.
- The paths, quotas, and revisions above are design intent from issues #4 to #8
  and may change when the work resumes.
- V3 changes nothing about V2: the released `v2` artifacts, splits, and tags are
  frozen, and the [versioning policy](versioning.md) still applies.
- The design inherits upstream sentence segmentation and language labels, so
  upstream segmentation or language errors would not be corrected locally.
- Coverage would be one sentence per H3 resolution-3 cell, which bounds
  geographic density rather than guaranteeing balanced regional representation.
- The description source is new in V3 and has no V2 rows to reuse, so it would
  depend entirely on fresh annotation.
