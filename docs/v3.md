# V3 workflow (candidate pool implemented, annotation paused)

V3 extends the human set from the 154 adjudicated V2 rows to 300 rows across
three sources. The streaming adapters are implemented, as are the V3 settings,
bounded candidate pool, and geographic preflight, but the annotation workflow remains
paused and not implemented: the repository runs only the V2 pipeline. V3 now
ships the settings profile, quota and seeding contracts, issue #5's three
source adapters, and issue #6's candidate-pool builder. There is no V3
annotation run or benchmark, so the benchmark to use remains
`data/benchmark/v2-adjudicated.csv`.

This page records the implemented adapter and candidate-pool contracts and the
remaining V3 design so the public documentation matches the paused state. Apart
from the settings, quotas, revisions, adapters, and candidate pool marked below
as shipped, the downstream behavior is planned in issues
[#8](https://github.com/NoeFlandre/landuse-sentence-relevance-golden-human-set/issues/8)
and
[#10](https://github.com/NoeFlandre/landuse-sentence-relevance-golden-human-set/issues/10),
not behavior that exists today. For the V2 workflow, see
[Data sources and models](data-sources.md) and [Annotation](annotation.md).

## Planned upstream datasets

The V3 adapters stream three public Hugging Face datasets and, as in V2, pin
each revision by commit SHA and never materialize a dataset locally.
`V3Settings` holds those pins, and they are deliberately not
environment-overridable.

| Source | Dataset | Pinned revision | Configuration/split the settings name |
| --- | --- | --- | --- |
| Description tag | [OSM polygon description tag](https://huggingface.co/datasets/NoeFlandre/osm-polygon-description-tag) | `fec858b679f5ee7e87f0ecfaaa6b7223b2a7f5e2` | `language-v1`/`train` sentence records with `language_code` and `sentences`, joined to `default`/`train` for geometry |
| Wikipedia | [OSM polygon Wikidata and Wikipedia](https://huggingface.co/datasets/NoeFlandre/osm-polygon-wikidata-and-wikipedia) | `f48c5aaaec6aecd63ecf5c195565cc2787597f1e` | `wikipedia_sentences`/`wikipedia_sentences` records with `language`, `project`, and `section_index` |
| Website tag | [OSM polygon website tag](https://huggingface.co/datasets/NoeFlandre/osm-polygon-website-tag) | `5c8e56a50b5679118a28aef057af002209f80a5e` | `default`/`polygons`, whose rows already carry the pre-split sentence columns and their `*_language` fields |

The website dataset publishes no separate sentence configuration: its
pre-split sentences are columns inside `default`/`polygons`, so the settings
read that split rather than a sentence-level one. The description dataset's
`language-v1` records carry no coordinates, which is why geometry is resolved
by the join described below.

### Planned sentence and language contract

All three upstream datasets already publish sentence-level records and language
metadata, so the V3 adapters consume them as they are:

- Sentences come from the upstream sentence fields. **No local splitter runs**:
  SaT-12L-sm is used by V2 today and is not used by the V3 adapters.
- English filtering uses upstream language metadata only. **No local language
  model runs**: CommonLingua is used by V2 today and is not used by the V3
  adapters.
- Wikipedia rows are restricted to `project=wikipedia` and English articles.
  **Wikivoyage is excluded**: the `wikivoyage_sentences` and
  `wikivoyage_sections` configurations are never read, matching the V2 rule
  that already excludes Wikivoyage.
- Wikipedia selection stays contextual: title-only and lead-only sentences are
  rejected, as in V2. The pinned revision publishes no `is_lead` or `is_title`
  column, so the rule is built on the columns it does publish and on what they
  hold in the recorded schema fixture:
    - the **lead** is `section_index` 0. Every lead row in the recorded shard
      also carries an empty `heading` at `level` 0 with an empty `section_path`,
      and no body row has an empty heading, so an empty heading is read as the
      lead too.
    - a **section title** reaches the sentence table as the first sentence of a
      body section, rendered with the MediaWiki edit marker (`[ edit ]` or
      `[ edit | edit source ]`). In the recorded shard all 592 body-section
      first sentences start with that marker and it appears nowhere else, so
      rejecting those rows drops heading lines only.
    - `sentence_index` alone never decides this: a body sentence that is not a
      heading line is kept whatever its index.
- Where sentence records carry no coordinates, geolocation is resolved with
  bounded streaming joins back to the polygon records, keeping provenance
  deterministic. The join reads the polygon or geometry side once across all of
  its shards and keeps only a small projection of each row — identity,
  coordinates, place name, region, and source URL — so a sentence still finds
  its polygon when the two rows fall in differently numbered shards. Both axes
  stay bounded: `max_rows_per_shard` rows per shard, and at most
  `max_join_entries` keys held at once.
- Provenance travels with every candidate, from the columns each pinned
  revision actually publishes:
    - `region` comes from the `region` column of the Wikipedia and website
      polygons. The description dataset publishes no `region`, so it is derived
      from `source_pbf` by stripping the extract suffixes
      (`afghanistan-latest.osm.pbf` → `afghanistan`). The sibling datasets of
      the same extract publish exactly that label, so the fallback reproduces
      the published value rather than inventing one.
    - `source_url` is the `osm_url` of a description geometry, the `website` or
      `contact_website` of a website row, and, for Wikipedia, a URL derived from
      `page_id` (`https://en.wikipedia.org/?curid=…`) because the sentence table
      publishes no URL column.

### Projections are checked against the recorded upstream schemas

`tests/fixtures/v3_upstream_schema.json` records the Parquet schema of all five
pinned streams, alongside the sampled facts the Wikipedia and region rules rest
on. The unit tests assert every projected column against that file, so a
projection can never name a column a pinned revision does not publish. Re-record
it with `uv run python scripts/record_v3_schema.py` when a pin changes.

`scripts/streaming_smoke.py` is the network gate: it opens all five V3 streams
with the exact production projections at the pinned revisions, reports any
projected column the stream does not return, and then builds a few real
candidates per source from one pinned shard each.

## Implemented candidate pool and geographic preflight

The candidate pool and geographic preflight are implemented in issue #6. The
builder streams the three adapters in the V3 source order and retains a bounded
deterministic reservoir of 1,600 cells per source by default. It then selects
400 cells per source with the existing maximin H3 stratification, enforcing one
candidate per globally unique resolution-3 cell. The larger reservoir gives the
geographic selector headroom while remaining bounded.

The builder reads only the compact V2 benchmark table to reserve every occupied
H3 cell and calculate the exact remaining source quotas (Wikipedia 1, website
46, and description 100 new rows). It rejects a pool before persistence when a
source lacks either the 400-candidate reservoir target or the number of fresh
rows still needed by the quota matrix. The candidates already carry the English
and contextual Wikipedia guarantees established by the V3 adapters.

Each source pass is checkpointed atomically to `V3Settings.candidate_progress_path`.
The checkpoint contains only the bounded candidate reservoir, the completed
source names, and a configuration/frozen-benchmark fingerprint. An interrupted
source is replayed deterministically; completed sources are skipped. A saved
pool is validated and reused on later runs, so upstream rows are streamed and
discarded rather than materialized locally.

## Planned V2 reuse and quota arithmetic

`data/benchmark/v2-adjudicated.csv` is immutable and would never be edited. V3
would seed its state from that file and annotate only the remaining rows.

| Source | Seeded from V2 | New annotations | V3 total (yes / no) |
| --- | --- | --- | --- |
| Wikipedia | 99 | 1 | 100 (50 / 50) |
| Website | 54 | 46 | 100 (50 / 50) |
| Description | 0 | 100 | 100 (50 / 50) |
| **Total** | **153** | **147** | **300** |

V2 holds 100 Wikipedia rows (49 yes, 51 no) and 54 website rows (31 yes, 23 no).
V3 would reuse 99 Wikipedia rows — one surplus `no` row left out of the V3 quota
— and add a single Wikipedia `yes` row to reach 50 / 50. All 54 website rows
would be reused, so 46 new website rows close the per-label gap, and the
description source would contribute 100 entirely new rows. Seeded V2 rows would
count toward the progress metrics but would never be presented for
reannotation.

## Planned storage and resume behavior

V3 keeps its own files beside the V2 ones on the Seagate project drive,
mirroring the V2 layout under a `v3` prefix rather than reusing any V2 path.
`V3Settings` defines the V3 paths below. Issue #6 writes only the candidate pool
and progress checkpoint; the V3 annotation session remains reserved for the
later annotation issue.

| Artifact | `Settings` (V2) path | `V3Settings` path |
| --- | --- | --- |
| Candidate pool | `results/candidates/v2/pool.json` | `results/candidates/v3/pool.json` |
| Candidate progress checkpoint | `results/candidates/v2/progress.json` | `results/candidates/v3/progress.json` |
| Annotation session | `results/annotations/sessions/v2-wikipedia.jsonl` | `results/annotations/sessions/v3.jsonl` |
| Runtime and auth state | `state/runtime-cache`, `state/huggingface-auth` | unchanged |

No V3 path overwrites V2 state. Candidate building checkpoints after each pass
and resumes by skipping completed source work. The annotation session will be appended
atomically, so labeling, relabeling, removing a row, quitting, and resuming
behave exactly as they do in V2 today. The UI would show total and per-source
progress, yes/no counts, and the remaining quotas, and would start only after
the candidate preflight succeeds.

## Limitations

- The annotation workflow remains paused and not implemented. There is no V3
  annotation UI path, published V3 split, or `v3` benchmark file under
  `data/benchmark/`.
- Everything above that is not marked as shipped is design intent from issues #7,
  #8, and #10, and may change when the work resumes.
- V3 changes nothing about V2: the released `v2` artifacts, splits, and tags are
  frozen, and the [versioning policy](versioning.md) still applies.
- The design inherits upstream sentence segmentation and language labels, so
  upstream segmentation or language errors would not be corrected locally.
- Coverage would be one sentence per H3 resolution-3 cell, which bounds
  geographic density rather than guaranteeing balanced regional representation.
- The description source is new in V3 and has no V2 rows to reuse, so it would
  depend entirely on fresh annotation.
